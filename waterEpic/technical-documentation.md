## 1. Overview

Maya needs to extract water usage data from Toro's **Lynx** irrigation control system for Adare Manor. Data is stored in a **SQL Server** database (`lynx_main`) accessible via standard SQL queries (read-only `SELECT` statements).

MSM (Toro's software/support partner) provided access and walked through the available data structures, their trade-offs, and recommended approach.

> **Confidentiality note:** MSM shared this database structure under a cooperative agreement specifically for the Adare Manor project. This is not typically disclosed to third parties. Handle with discretion.

## 2. Key Concept: Irrigation Day vs Calendar Day

**This is critical to understand before working with any table.**

Lynx uses a concept of an **irrigation day** that does **not** align with a calendar day:

| Concept | Value (Adare Manor) |
|---------|---------------------|
| Irrigation day start time | **3:55 PM** |
| Irrigation day span | 3:55 PM Day 1 → 3:55 PM Day 2 |
| Database date boundary | **Midnight** |

**Implication:** A single "irrigation day" (e.g., Feb 17th from the customer's perspective) spans **two calendar dates** in the database:
- Feb 17th: 3:55 PM → midnight
- Feb 18th: midnight → 3:55 PM

The irrigation day start time is configurable per site (`begin_water_daytime` setting in Lynx). Most customers leave it at the default, but always verify.

## 3. Data Tables

### 3.1 `water_use` — Aggregated Daily Summary

| Attribute | Detail |
|-----------|--------|
| **Granularity** | Per hole, per zone, per day |
| **Time basis** | Midnight to midnight (NOT irrigation day) |
| **Retention** | Permanent |
| **Source** | Aggregated from `water_use_upload` after 7 days |

**Pros:**
- Long-term historical data
- Per-hole, per-zone breakdown

**Cons:**
- Cannot split data by irrigation day (midnight boundary only)
- Lump storage — cannot break apart into station-level detail
- Loses granularity from the upload table

**Verdict:** Useful for long-term trends. **Not recommended** as primary reporting source due to loss of granularity and irrigation day misalignment.

---

### 3.2 `water_use_upload` — Satellite Actual Data (Recommended for Accuracy)

| Attribute | Detail |
|-----------|--------|
| **Granularity** | Per station (most granular available) |
| **Time basis** | Aligned with irrigation day |
| **Retention** | **7 days only** — then aggregated into `water_use` |
| **Source** | Satellite faceplate reports what actually ran |

**Key fields:**
| Field | Description |
|-------|-------------|
| `SUID` | System Unique ID — unique identifier per station |
| `duration` | Runtime in **seconds** |
| `auto_duration` | Duration of auto-scheduled (programmed) irrigation |
| `total_duration` | Total irrigation duration (auto + manual) |
| `station_flow` | Flow rate for the station |

**Calculating manual watering:**
```
manual_duration = total_duration - auto_duration
```

**Calculating volume:**
```
total_gallons = (duration / 60) * station_flow
-- or convert to cubic meters as needed
```

**Joining to get station location:**
```sql
-- Join water_use_upload to station table on SUID
-- to get station_descriptor (e.g., "1GR2")
SELECT wu.*, s.station_descriptor
FROM water_use_upload wu
JOIN station s ON wu.SUID = s.SUID
```

**Pros:**
- **Most accurate data** — reports what the faceplate actually ran
- Station-level granularity
- Captures both auto and manual watering
- Can aggregate up to any level (station → zone → hole → course)

**Cons:**
- **7-day retention only** — must be captured/synced regularly
- Depends on satellite communication (every 2 hours, on even hours)
- **Overseed risk:** During overseed periods (~twice/year), continuous all-day watering prevents the upload trigger from firing, causing data gaps
- Upload only triggers after: ≥1 hour of no irrigation AND hitting an even hour

**Upload trigger rules:**
1. Irrigation must have stopped for ≥1 hour
2. Must hit an even hour (2:00, 4:00, 6:00, etc.)
3. Must occur before the irrigation day ends (before 3:55 PM for Adare)
4. Last possible trigger: 2:00 PM (to allow 1-hour gap before 3:55 PM start)

**Verdict:** **Best source for actual water usage.** Must sync within 7-day window. Understand communication and overseed limitations.

---

### 3.3 `schedule_activity` — Scheduled Irrigation Intent

| Attribute | Detail |
|-----------|--------|
| **Granularity** | Per station |
| **Time basis** | Created at irrigation day start (3:55 PM for Adare) |
| **Source** | Schedule generated by Lynx software |

**What it captures:** What the system **intended** to irrigate for the day.

**Does NOT capture:**
- Manual watering
- Rain holds / cancellations
- Schedule changes made after initial creation

**Pros:**
- Reliable — created at a known time
- Not dependent on satellite communication
- Good for reporting "what was planned"

**Cons:**
- Does not reflect what actually happened
- If customer modifies schedule after creation and re-downloads, only latest schedule is retained
- Cannot capture rain holds or manual interventions

---

### 3.4 `schedule_activity_download` — Confirmed Schedule at Faceplate (Recommended for Scheduled Data)

| Attribute | Detail |
|-----------|--------|
| **Granularity** | Per station |
| **Time basis** | Created when schedule is successfully sent to faceplate |
| **Source** | Confirmation of schedule delivery to satellite hardware |

**Key fields:**
| Field | Description |
|-------|-------------|
| `station_descriptor` | Station location tag (e.g., "1GR2") |
| `duration` | Scheduled runtime in **seconds** |
| `station_flow` | Flow rate |

**Calculating volume from schedule:**
```sql
-- Duration is in seconds
-- total_gallons = (duration_seconds / 60) * station_flow
SELECT
    station_descriptor,
    duration,
    station_flow,
    (duration / 60.0) * station_flow AS total_gallons
FROM schedule_activity_download
WHERE [date_filters]
```

**Pros:**
- Confirms schedule was received by faceplate
- If faceplate didn't receive download → no record (honest gap vs false data)
- Shaun Bowles' recommended table for scheduled reporting

**Cons:**
- Does not capture manual watering
- Does not capture rain holds / cancellations (schedule still shows as downloaded even if held)
- During overseed: multiple downloads per day as schedules are chunked and sent in batches
- If satellite doesn't communicate → no download record

**Verdict:** **Best source for "what was scheduled."** Pair with `water_use_upload` for "what actually happened."

## 4. Station Naming Convention

Station descriptors follow an alphanumeric format:

```
1GR2
│││└─ Station number (2nd station in this area)
│└┘── Area code (GR = Green)
└──── Hole number (Hole 1)
```

**Important:**
- Customers can edit station display tags — the label may change
- Always join on `SUID` (System Unique ID) for reliable identification
- Parse `station_descriptor` for display/grouping purposes only
- If customer changes tag format, SUID remains stable

**Aggregation:** Parse the area code from `station_descriptor` to group stations into zones/areas for higher-level reporting.

## 5. Recommended Approach for Maya Integration

### Primary: `schedule_activity_download`
- Use as the base reporting table for "what was scheduled"
- Reliable, not dependent on real-time communication
- Best queried after irrigation day ends (e.g., 1:00 AM safe window)

### Secondary: `water_use_upload`
- Use to capture **actual** irrigation (including manual watering)
- **Must sync within 7-day window** before data moves to `water_use`
- Cross-reference with schedule to identify variances (manual watering, rain holds, partial runs)

### Fallback: `water_use`
- Use for historical / long-term trend analysis only
- Midnight-to-midnight boundary — cannot align to irrigation day

## 6. Known Risks & Limitations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Satellite communication failure** | No data in `water_use_upload` or `schedule_activity_download` | Accept gap; cannot report on what can't communicate. Not Maya's responsibility. |
| **Overseed periods** (~2x/year) | `water_use_upload` may have no data for days with continuous all-day watering | Fall back to `schedule_activity_download` for those periods. Inform customer of limitation. |
| **7-day retention on `water_use_upload`** | Data lost if not captured within window | Implement daily sync job to pull data regularly |
| **Rain hold / cancellation** | `schedule_activity_download` still shows the schedule as downloaded | Only `water_use_upload` reflects actual run (zero or partial runtimes) |
| **Multiple downloads during overseed** | Schedule is chunked into batches, creating multiple download records per day | Account for multiple records per station per day during overseed |
| **Customer edits station tags** | Display names may change | Always join on `SUID`, use `station_descriptor` for display only |
| **Irrigation day ≠ calendar day** | Data spans two calendar dates | Always account for irrigation day boundaries (3:55 PM → 3:55 PM) |
| **Units (gallons vs cubic meters)** | Varies by customer | Adare Manor TBC — verify with customer. Calculation is the same, just label differs. |

## 8. Integration Architecture — Maya Lynx Connector

_Decision made: 2026-02-25_

### Problem

Lynx runs on-premise at each club on a local SQL Server. Maya is cloud (AWS/Laravel). We need a solution that works across 100+ clubs, not just Adare Manor. Clubs typically have secure networks/VPNs — we can't rely on inbound connections.

### Decision: Deployable Sync Agent + Cloud Ingest API

**Agent side (installed at each club):**

| Attribute | Detail |
|-----------|--------|
| **Runtime** | Python packaged as Windows executable (PyInstaller → .exe) |
| **Deployment** | Windows installer (.msi), one-time setup |
| **Schedule** | Daily via Windows Service or Scheduled Task |
| **Config** | Local config file: Lynx DB credentials, Maya API key, site settings |
| **Communication** | Outbound HTTPS only (port 443) — no firewall/VPN changes needed |
| **Installation** | MSM tech or club IT runs installer, enters Lynx DB creds + Maya API key |

**What the agent does each run:**
1. Queries `water_use_upload` (actuals — primary source)
2. Queries `schedule_activity_download` (scheduled — fallback source)
3. Reconciles: uses actuals where available, fills gaps with scheduled data
4. Aggregates station-level data → zone level (parses `station_descriptor` area codes)
5. Handles irrigation day boundary (3:55 PM span, configurable per site via `begin_water_daytime`)
6. Detects units from Lynx config (gallons or m³), normalizes
7. Pushes one clean daily-per-zone dataset to Maya's ingest API over HTTPS
8. Reports sync status (success/failure/row counts) for health monitoring

**Cloud side (Maya backend — Laravel):**

| Component | Detail |
|-----------|--------|
| **Ingest API** | Laravel endpoint — receives + validates data from agents |
| **Auth** | Per-club API key |
| **Club config** | Units, timezone, irrigation day start, zone mapping |
| **Health monitoring** | Track last sync per club, alert on missed syncs |
| **Data layer** | Feeds directly into Water Page 2.0 (Epic 253) |

### Why this approach

- **Scales to 100+ clubs** — same package, config is the only variable
- **No network changes** — outbound HTTPS works on any club network
- **Zero effort for clubs** — install once, runs automatically
- **Monitorable** — Maya sees sync health for every club from the cloud side
- **Commercial play** — one-time installation fee and/or bundled as Water module. MSM could distribute.

### Reconciliation logic (the smart part)

The user sees **one number per zone per day** in Maya. Behind the scenes:
- `water_use_upload` (actuals) is the primary source — most accurate, captures manual watering and rain holds
- `schedule_activity_download` fills gaps when actuals are missing (overseed periods, satellite comm failures)
- `water_use` (aggregated) used only for historical backfill if needed
- The user never sees "scheduled vs actual" — just clean water usage data

### Granularity

| Dimension | Value | Rationale |
|-----------|-------|-----------|
| **Spatial** | Per zone (e.g., Hole 1 Green) | Maps to Maya "outflow" concept in Water Page 2.0 |
| **Temporal** | Daily | Matches Water Page insight cards, calendar, records table |
| **Aggregation** | Stations → zones via `station_descriptor` area code | Individual sprinkler data aggregated up |

### Pilot

Adare Manor is the first deployment. Validate the full loop (agent install → sync → Water Page display), then roll out to additional clubs.
